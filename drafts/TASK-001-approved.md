## 9.5 多个 Agent 出现后，重点转向阶段治理

即使任务已经适合使用 Agent，再增加 Agent 也不会自动让工作流更成熟。多 Agent 更适合那些能够拆开、结果可以检查，而且并行推进确实能减少等待时间的任务。如果任务彼此高度依赖、规则仍在变化，或者每一步都需要重新判断研究方向，多开几个 Agent 反而会增加协调和复核成本。

这时，一个重要变化是要区分**执行性问题**与**战略性问题**。执行性问题可以在已经确认的目标和规则内解决，例如文件是否完整、链接是否有效、代码是否通过测试、产出是否符合既定规格。战略性问题则会改变项目本身，例如需要调整研究问题、分析规格、证据标准、任务范围或验收条件。前一类问题可以让 Agent 在明确边界内自行处理；遇到后一类问题时，应暂停执行，重新交给研究者判断。

这样的区分也改变了对话模型在工作流中的位置。如果每个 Agent 做完一步，都必须回到同一个对话讨论‘下一步做什么’，表面上虽然用了多个 Agent，实际流程仍然是串行的。更有效的方式，是在一个阶段开始前先确定目标、任务边界、验收标准和需要升级的问题，再让 Agent 在这些条件内推进。只有当既有条件不足以继续决策时，才重新进入更深的分析。

因此，协作所依赖的状态也不能只存在于聊天记录中。第8章介绍的项目入口、当前有效状态、决定记录和交接页，可以进一步成为不同 Agent 接力工作的共同参照。这里并不意味着把所有研究材料都放入 Git 或任何单一平台：敏感数据和受限材料仍应保存在合适的位置，项目文件保存的是可以安全共享的规格、已经确认的决定、当前状态以及指向受控材料的必要信息。

对于影响较大、需要反复执行或可能交接给其他 Agent 的工作，还可以把一次性的任务说明进一步固定成**任务规格**。例如，一项“结果—正文一致性检查”可以写成：

> **目标：**核对当前确认结果表与正文中的样本量、模型名称、系数和表图编号。  
> **输入：**当前确认结果表、待检查正文。  
> **输出：**问题列表及对应位置，不直接改写正文。  
> **验收：**正文中的所有报告数字都能追溯到当前结果表中的对应项。  
> **禁止：**改变分析、补造结果或自动修改正式结论。  
> **升级：**若正文与结果来自不同分析版本，停止执行，由研究者确认当前有效版本。

有了这样的边界，不同 Agent 才适合在彼此依赖较少的任务上并行：一个检查链接和引用，一个核对代码与输出，一个整理交接材料。并行主要减少的是等待时间，并不会自动减少计算量，也会带来额外的协调成本。

第二个 Agent 也不能被当作第二份独立证据。它可以帮助发现遗漏、测试实现或从另一个角度检查结果，但如果多个 Agent 依赖相同材料、假设或相近模型，它们仍可能产生相关错误。第10章的原则仍然适用：验证、独立审计、人工复核和复现承担不同功能，“两个模型意见一致”本身不能替代来源、方法和研究者的判断。多 Agent 工作流真正改变的，是研究者不再需要逐步告诉每个工具下一步做什么，而是更多地负责定义阶段、设置边界、处理升级问题，并对最终结果作出验收。

本章应用：判断一个重复任务应该停在哪一层

从你最近一个月重复至少两次的任务中选一个。先写清不变输入、不变步骤、输出、失败状态和人工检查点，再决定它应该停在哪一层。若这个任务确实需要多个 Agent 协同，再补写阶段目标、各任务边界、验收标准和升级条件。能用简单形式可靠完成，就不要为了“高级”继续升级。
