# 两站迭代经验与作者工作台的任务目的

整理日期：2026-10-18。范围：本对话从全量审查、主手册 v1.3 写作与发布、动态指南 v0.12 更新与发布，到私人作者工作台设计。以用户反馈及仓库完成记录为依据；这里只提炼可复用判断，不把聊天或检查日志转存成项目数据库。

## 编辑与读者经验

| 本轮暴露的问题 | 应保留的经验 | 后续怎么用 |
| --- | --- | --- |
| 原稿原则正确，但正面能力与操作解释偏少 | 内容价值看读者能完成什么；篇幅只为解释、判断和练习服务 | 每章明确起点、材料、AI 能做的工作、研究者的判断、可检查产物和后续动作 |
| 方法学习一度像独立的方法教材 | 方法知识通过“怎样用 AI 学会并用好它”组织 | 展示如何提问、比较解释、运行小例子、发现误解、迁移到自己的研究；保持必要理论深度 |
| 部分章节可读了，工作流仍未展开 | 工作流需要跨步骤、跨轮次和跨会话的实际衔接 | 同一案例展示材料如何变化、产物怎样成为下一步输入，以及中断后如何继续 |
| “工作环境”等名称让只用过聊天工具的读者摸不着头脑 | 先给真实任务、产品名字和动作，再解释概念 | 导读先让读者看到 AI 还能帮助完成哪些研究工作；术语在需要处解释，少设必学词表 |
| 用户举豆包例子后，候选过度重复同一品牌 | 例子用来说明读者起点，不能被误读为唯一产品路线 | 千问、DeepSeek、豆包及国际产品按任务同等考虑；不机械轮换，也不按品牌划初级/高级 |
| 防御性语句进入正文，例如解释为什么举某品牌 | 编辑过程不应妨碍正文阅读 | 删除编辑自辩、假想反对意见和重复劝告；保留影响操作、推断和科学判断的真实条件 |
| “润色”容易被误当成缩写 | 自然中文与详细解释可以同时成立 | 使用 Humanizer-zh 检查空话和模板句，但保护事实、数字、限定、关系、案例及引用 |
| 产品名称、模型、聊天应用、文件执行工具容易混用 | 具体能力属于对应入口和版本，不能从模型名字推导整个产品功能 | 首次出现说明实际入口和用途；当前产品事实留在指南并按官方来源核查 |
| 一套教程列太多产品会重复膨胀 | 按科研任务组织主线，产品页做支持 | 一个核心任务先给完整操作路线，再补有实质差别的替代路线；国内路线应能实际起步 |
| API、Agent、vibe coding 容易变成必经阶梯 | 进阶工具解决具体需求，普通对话也应能完成有价值的首次任务 | 让读者按需求选择，不把技术栈复杂度当研究能力水平 |

这些原则来自 [TASK-006](../tasks/TASK-006-chinese-editorial-revision.md)、[TASK-007](../tasks/TASK-007-literature-design-drafts.md)、[TASK-008](../tasks/TASK-008-workflow-chapters.md)、[TASK-009](../tasks/TASK-009-reader-entry.md)、[TASK-010](../tasks/TASK-010-prose-and-product-balance.md) 和本对话中的后续反馈。润色参考为 [Humanizer-zh](https://github.com/op7418/Humanizer-zh/blob/main/SKILL.md)；技能不是事实核验工具，不以机械词表替代编辑判断。

## 两站分工、材料和证据

- 主手册维护稳定的方法解释、研究判断和连贯案例；指南维护实际产品入口、预算、地区与操作步骤。互链具体章节，不复制两份需要同时更新的方法正文。
- 指南应能独立帮助新手开始，再连接主手册深读。产品目录服务于任务，不以收录数量判断完成度。
- 复用固定版本的教学材料，明确文件从哪里取得。源数据、参考结果和任务演示保持一致，不为新教程复制出另一套未核对的数字。
- 区分六行练习、问卷数据和纵向数据；两名虚构说话者的六个片段不等于六名受访者；读取结果表生成第二轮报告不等于重新拟合模型。这些案例显示：文字衔接也需要逐项检查对象、层次和动作。
- 当前价格、套餐、地区、功能状态分别核验；不强套统一美元档位，不把未来生效政策写成现行规定。官方资料冲突时保留版本与适用范围。
- 阅读官方说明、离线测试、真实产品操作是不同证据。未实测范围集中说明，各步骤只保留影响当前行动的限制；不靠重复免责声明替代核查。

指南依据位于配套仓库 `tasks/ITERATION-v0.12.md`、`docs/v0.12-candidate-review.md` 与 `tasks/RELEASE-v0.12.md`。

## 执行、整合和发布经验

- 分清写作授权、候选验收、正式整合和发布授权。已获明确范围的工作持续完成；不要为每个文件或机械步骤重复请求批准，也不要把上一阶段授权延伸到新的战略范围。
- 将需要综合判断的工作用于结构、论证、案例和中文；文件修改、构建、Git、测试及状态维护由执行工具处理。没有独立交付必要时，不为了并行而拆出多个 Agent。
- 以可审阅的完整候选作为阶段成果，避免停留在蓝图、零散段落或大量流程文档。阶段状态应由实际产物和检查决定。
- 全站兼容包括页面路径、标题锚点、下载地址与材料内容。指南 v0.12 补回 90 个旧标题定位，保留 v0.11 的 118 个锚点，说明“URL 不变”并不足够。参见指南发布任务。
- 构建通过不等于可用：需要代表性阅读、窄屏、实际文件打开与任务运行。主手册纸面版还需要目录、原生公式、链接和最终逐页呈现检查，参见 [TASK-014](../tasks/TASK-014-v1.3-release.md) 与[导出说明](../publication/README.md)。
- 发布后核验公开页面与下载，而不只检查本地构建。二进制文件逐字节比较；文本比较说明换行规范。既有标签、Release 与资产保留基线。
- `main`、阶段文件、决策和任务负责可恢复状态；聊天、截图、原始校验输出不成为另一套事实来源。临时 QA 留在忽略目录，治理文件只写必要结论及入口。
- 后续状态记录必须清楚区分历史阶段已经完成与新阶段正在设计，不能用一条陈旧的“本轮 DONE”覆盖新的任务。

## 本轮新目的：让作者在阅读现场完成编辑

当前阅读页面与源文件分开，作者发现问题后需要定位源码，或再次转述给 Agent。这个切换成本使小修改和临时想法容易丢失。本轮要设计并记录一条完整技术路线，使作者能够方便进入、可靠保存、看到私人草稿，并在下一轮集中整合。

本轮新确认的原则：

1. **编辑随时保存，下一轮集中合并。** 保存不是实时改写公开网页，也不直接修改正式源文件；私人草稿与发布版状态分别显示。
2. **入口属于核心功能。** 桌面一键启动与从阅读页跳到同章都要考虑服务未启动、首次安装和浏览器限制；不能要求记端口或重新找文件。
3. **已经写好的修改、待实现的意见与暂存想法分别处理。** 作者身份明确权限，具体意图决定执行；作者随手记不自动成为本轮要求。
4. **保存上下文和版本。** 原文快照、引文、章节和前后文随记录保存。文字移动后可重新定位，有冲突时不静默覆盖。
5. **下一轮保护作者劳动。** 先精确整合作者改字，再开展 AI 写作；逐条给出处理回执，新修订和未处理意见不被批次完成动作吞掉。
6. **私人资料有独立持久来源。** 不只放浏览器缓存，不放可清理的 QA 目录，不随公共仓库或网站发布。记录库应可导出、备份和恢复。
7. **两站共用小工具。** 优先实现个人写作体验；公开评论不在本轮，跨设备、多人协作和自动模型运行后置。

详细技术提案见[作者工作台设计](author-workbench-design.md)。以上已确认的行为原则可以进入治理；数据库、启动协议、源码映射和实现工作包仍属于待审设计，不能写成已实现能力或已获发布批准。

## 哪些内容进入治理

| 文件 | 本轮应记录 | 不应放入 |
| --- | --- | --- |
| 两库 AGENTS.md | 稳定编辑原则、私人修改的处理边界、当前任务入口 | 详细数据表、接口参数、全部实施步骤 |
| 主库 DECISIONS.md | 用户已确认的保存/合并、入口和范围原则 | 将尚未审阅的技术选型写成批准决定 |
| CURRENT_PHASE / PROJECT_STATUS | 新设计阶段、实际授权、交付与下一步 | 继承已结束发布阶段的执行权限 |
| TASK-015 | 设计任务和验收、实施路线入口 | 以本轮设计任务冒充已批准的实现任务 |
| HANDOFF | 当前阶段及继续工作需要的少量链接 | 重复整份设计和全部历史日志 |

本文件保存整体经验；治理只提取会改变后续行为的部分。正文不会因为这次治理整理而自动改写。
